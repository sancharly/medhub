# TS-007 — Clinical entries and attachment verification

## Scope

Software requirements covered: SR-012, SR-013, SR-023.
Software items under test: SI-CLINICAL, SI-ATTACH, SI-FE-CORE.
Levels: unit, integration.

## Preconditions and environment

Build: branch `bug/soup-pinning` (CR-001), which holds `backend/tests/test_object_storage.py` (TC-007.5); branch `bug/minio-object-store` (CR-002) for TC-007.6 to TC-007.8; branch `fix/review-2026-07-security` (CR-004) for TC-007.9 and TC-007.10; branch `fix/review-2026-07-reliability` (CR-006) for TC-007.12, TC-007.13, TC-007.14 and TC-007.15. Backend Python 3.12 with the
dependencies locked in `backend/uv.lock`; frontend Node 24 LTS (build stage node:24.22.2-trixie-slim; CI node-version 24) with `frontend/package-lock.json`.
Unit and service tests run with no external services (in-memory repositories and a fake object store, `backend/tests/attachments/fake_object_store.py`). The real-store cases of TC-007.13 run only with `OBJECT_STORE_INTEGRATION=1` against SeaweedFS 4.51 (SOUP-036), marked `object_store` like the other real-service tests. TC-007.5 builds the real boto3 S3 client from the locked SDK; no object-storage service is needed. TC-007.6, TC-007.9 (one case), TC-007.10 (audit persistence), TC-007.14 and TC-007.15 are *real DB*. Tests marked *real DB* require a
PostgreSQL 16 container through testcontainers and therefore a working Docker daemon.
Exact SOUP versions: the `soup` records in [`../../soup/`](../../soup/).

## Acceptance criteria (class B unit level, §5.5.3)

- Data flow: the object is written before the metadata commit, so a failure leaves no dangling reference.
- Resource allocation: an upload is never held whole in memory; the peak allocation does not grow with the object size (TC-007.12, PRB-008 upload half) and a download is never held whole either: two bounded passes of 64 KiB chunks (TC-007.13, PRB-008 download half).
- Boundary: attachment exactly at the size limit (150 MiB accepted, one byte more refused; TC-007.12).
- Data flow: a success response is sent only after the request transaction has committed, and a failed commit is a 5xx (TC-007.14, SR-012 AC 5, ADR-0023); the download audit rows are committed before the first body byte and the download holds no pooled connection while transferring (TC-007.15, SR-023 AC 10).
- Fault handling: an object whose SHA-256 differs from the stored checksum is never returned, on any download path including DICOM (SR-013 AC 5); on the streaming path no byte is sent before the whole object has matched, an object replaced between the two passes is refused by the conditional second read, and a mismatch at the end of the second pass aborts the transfer (TC-007.13). A download that fails on the server is never unaudited: a FAILURE `ATTACHMENT_ACCESS` row is committed (SR-023 AC 2, ADR-0016). A file name never makes a download fail or the header malformed (SR-013 AC 3).
